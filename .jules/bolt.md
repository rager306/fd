## 2023-10-27 - Cache Key Generation Overhead
**Learning:** In Go, using `fmt.Sprintf` for constructing strings in highly-frequent hot paths (like cache lookups per embedding input) causes measurable overhead due to reflection and interface boxing, adding unnecessary allocations compared to standard string concatenation.
**Action:** Replace `fmt.Sprintf` with `strconv.Itoa` and simple string concatenation `+` in hot paths, and consider adding fast-path hardcoded values for frequently used parameters (e.g. dimensions 512, 1024) to avoid string conversion entirely.
## 2025-05-18 - Avoid manual inlining and expensive hashing in hot paths
**Learning:** Manually replacing `strings.HasPrefix` with slice bounds checking offers zero performance benefit because the Go compiler automatically inlines it. Furthermore, adding cryptographic hashing (like `sha256.Sum256`) to every incoming request inside HTTP middleware (like authentication), even if well-intentioned for security, severely degrades throughput and contradicts the goal of performance optimization.
**Action:** Do not manually inline standard library string functions; trust the compiler. When optimizing, rigorously benchmark both the "before" and "after" state to guarantee an actual net performance increase, especially when introducing new security functions.
## 2025-05-18 - Go syntax import ordering and artifact hygiene
**Learning:** When using `sed` or bash scripts to blindly inject new constants to resolve `goconst` linter errors, placing them directly after the `package` declaration (before the `import` block) results in `syntax error: imports must appear before other declarations`. Additionally, leaving single-use bash scripts (`.sh` files) checked into the project directory is a major hygiene violation that blocks PR submission.
**Action:** Always inject package-level variables or constants *after* the `import` block to satisfy Go's strict ordering rules. Always explicitly delete any temporary scratchpad files or bash scripts before requesting code review or submitting a PR.
## 2025-05-18 - Tool usage for dependency vulnerability resolution
**Learning:** `govulncheck` is an essential tool for identifying vulnerabilities in dependencies. The process to fix such an issue involves identifying the vulnerable package version, updating it in the relevant `go.mod` file (using `go get`), and then running `go mod tidy`. Finally, `govulncheck` should be re-run locally to confirm the issue is resolved before proposing the fix to CI.
**Action:** When a Check Suite failure indicates a dependency vulnerability, use `go get <package>@<fixed-version>` followed by `go mod tidy` in the correct directory. Then verify using `govulncheck`.
