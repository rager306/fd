## 2023-10-27 - Cache Key Generation Overhead
**Learning:** In Go, using `fmt.Sprintf` for constructing strings in highly-frequent hot paths (like cache lookups per embedding input) causes measurable overhead due to reflection and interface boxing, adding unnecessary allocations compared to standard string concatenation.
**Action:** Replace `fmt.Sprintf` with `strconv.Itoa` and simple string concatenation `+` in hot paths, and consider adding fast-path hardcoded values for frequently used parameters (e.g. dimensions 512, 1024) to avoid string conversion entirely.
## 2024-05-19 - Safe Stack Allocation and Micro-optimizations Context
**Learning:** Hardcoding dimensional branches (e.g., 512, 1024) and allocating arbitrary buffers (e.g., 256 bytes) inside a `key` generation function without bounds checking can introduce vulnerabilities if `namespace + prefix` strings are dynamically populated and exceed the buffer limit. Furthermore, optimizing a few heap allocations immediately before a multi-millisecond network (Redis) call can be considered a premature micro-optimization if it degrades code readability and repeats logic (violating DRY).
**Action:** When finding hot paths, prioritize safe, self-contained optimizations. For hashing like ETags or ID generation which generate fixed-length hex responses, encoding directly into exact-sized stack arrays (e.g. `var buf [66]byte` for `"` + 64 hex chars + `"`) is 100% bounds-safe, removes heap allocations, maintains perfect readability, and provides measurable speedup without risking panics.
